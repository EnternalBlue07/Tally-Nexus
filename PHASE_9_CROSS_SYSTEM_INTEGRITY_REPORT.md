## 1. EXECUTIVE SUMMARY

During real-browser visual QA and end-to-end verification, two critical reliability defects were identified and diagnosed down to their root causes:

1. **Bug A (AI SLA Judge Foreign Key Failure):** `POST /api/judge/evaluate` returned `HTTP 500: FOREIGN KEY constraint failed` when executed against the live SQLite ledger because table `system_events` enforces a strict foreign key `REFERENCES settlement_cycles(cycle_id)`, and standalone evaluations lacked parent cycle and agent records. The frontend modal previously fell back to static mock text (`COMPLETED`, `$50.00 USD`).
2. **Bug B (PayPal Authoritative Verification False Match):** Modal inspection of internal simulated demonstration captures (e.g. `CAP-33AD6CA3-911` / `CAP-8F390CDE-058`) against live PayPal sandbox rails returned `404 RESOURCE_NOT_FOUND`, but the UI displayed `DATABASE RECORD VERIFIED` because local SQLite row existence was conflated with live provider verification.

Both root causes have been resolved at the database transaction layer, Express API layer, and frontend UI layer without disabling safety triggers, fabricating provider responses, or creating mock workarounds.

## 2. ROOT CAUSE ANALYSIS & CODE CHANGES

### Bug A: AI SLA Judge Foreign Key Failure

* **Root Cause:** In `src/db/schema.sql` line 217:
  ```sql
  CREATE TABLE IF NOT EXISTS system_events (
      sequence_id   INTEGER PRIMARY KEY AUTOINCREMENT,
      event_id      TEXT NOT NULL UNIQUE,
      event_type    TEXT NOT NULL,
      cycle_id      TEXT REFERENCES settlement_cycles(cycle_id) ON DELETE RESTRICT,
      payload_json  TEXT NOT NULL,
      emitted_at    TEXT NOT NULL DEFAULT (datetime('now', 'utc'))
  );
  ```
  When `LlmJudgeService.evaluateTask` executed, it attempted an `INSERT INTO system_events` referencing `context.cycleId` (`cyc_ai_live`). Because no record existed in `settlement_cycles`, SQLite immediately aborted with `FOREIGN KEY constraint failed`.
* **Fix Implemented:** In `src/judge/llm-judge-service.ts`, record persistence was wrapped in an atomic `db.withTransaction` ensuring parent-child creation order:
  1. Parent 1 & 2: Debtor & Creditor agents registered in `agents` with deterministic Ed25519 public key hashes.
  2. Parent 3: Settlement cycle registered in `settlement_cycles` with status `'CREATED'`.
  3. Parent 4: Task registered in `tasks` with status `'SUBMITTED'`.
  4. Child 1: System outbox event emitted in `system_events` with valid `cycle_id` reference.
  5. API Router: `src/api/routes.ts` calls `SlaJudge.evaluateTask` with `evaluatorType: 'LLM_JUDGE'` to atomically persist the verdict in `task_verdicts` and transition task status.
* **Frontend Error Guard:** In `src/dashboard/dashboard-html.ts`, `testLiveAiJudge` checks `res.ok` and `data.error`. If persistence fails, the UI immediately displays a prominent red banner and status badge: `AI JUDGE EVALUATION FAILED`, with `PERSISTENCE FAILED` and the exact error payload.

### Bug B: PayPal Authoritative Verification Separation

* **Root Cause:** In `src/dashboard/dashboard-html.ts`, `renderVerifyResult` contained a binary condition:
  ```javascript
  if (data.storedEvidenceMatched) {
    evMatch.textContent = 'MATCHED CANONICAL EVIDENCE';
  } else {
    evMatch.textContent = 'DATABASE RECORD VERIFIED'; // False positive on 404!
  }
  ```
  When simulated captures generated by `MockPayPalClient` during flagship runs (`CAP-...`) were verified against `api-m.sandbox.paypal.com`, PayPal correctly returned `404 RESOURCE_NOT_FOUND`. The client received `dbRecordMatched: true` and displayed `DATABASE RECORD VERIFIED`, misleading the user into believing the transaction existed on PayPal rails.
* **Fix Implemented:**
  1. **API Layer (`src/api/routes.ts`):** Established distinct verification statuses:
     - `VERIFIED_ON_PAYPAL_SANDBOX` / `PROVIDER_VERIFIED`: Live 200 match from PayPal API.
     - `LOCAL_RECORD_FOUND`: Record exists in local SQLite ledger, but is absent from live PayPal rails (`isSimulatedRecord: true`, `providerStatus: 'NOT_FOUND'`).
     - `STORED_CANONICAL_EVIDENCE` / `EVIDENCE_VERIFIED`: Authenticated canonical test run evidence (`7PV82720RX415822V` / `N4M49PUHNCNQ4`).
     - `EVIDENCE_MISMATCH`: Local ledger amount/currency differs from authoritative PayPal response.
     - `PROVIDER_PENDING`: Batch or capture in `PENDING` / `PROCESSING` state.
     - `PROVIDER_ERROR`: PayPal returns 5xx or network transport fails.
     - `RESOURCE_NOT_FOUND`: Identifier unknown to both ledger and provider.
  2. **Frontend UI Layer (`src/dashboard/dashboard-html.ts`):**
     - Simulated records display a blue info badge: `LOCAL LEDGER RECORD FOUND (SIMULATED)`, `NOT_FOUND_ON_RAILS` in red, and `SIMULATED DEMO RECORD`.
     - Prominent banner: `"ℹ️ Simulated Record: Local ledger entry exists, but transaction was not broadcast to live PayPal rails."`
     - Real live verified captures (`7PV82720RX415822V`) display green badge: `VERIFIED ON PAYPAL SANDBOX`, `COMPLETED`, `MATCHED CANONICAL PROOF`, and PayPal Debug ID.
