## 1. Comprehensive Financial Failure Matrix

| Failure Scenario | Detection Mechanism | Durable System State | Retry Policy | Recovery & Self-Healing Action | User & Demo Visibility |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1. OAuth Token Expiry / Failure** | HTTP 401 Unauthorized from PayPal REST API. | In-memory token cleared; DB state untouched. | Exponential backoff (1s, 2s, 4s; max 3 retries). | Re-authenticates via Basic Auth `POST /v1/oauth2/token` and updates token cache. | Transparent to user; subtle network retry indicator in Command console. |
| **2. Order Creation Timeout** | Socket timeout ($\ge 10\text{s}$) or HTTP 504 on `POST /v2/checkout/orders`. | `settlement_cycles.status = 'FIREWALL_APPROVED'`. No `paypal_orders` record. | Retry with **exact same** `PayPal-Request-Id` (`"nexus_order_" + cycle_id`). | Idempotent PayPal lookup: PayPal returns either the created order or accepts fresh creation. | Shows "Creating Order (Retrying)..."; no duplicate order created. |
| **3. Debtor Approval Abandonment** | User closes PayPal checkout tab or clicks "Cancel and return to merchant". | `paypal_orders.status = 'CANCELLED'`; `settlement_cycles.status = 'COLLECTION_FAILED'`. | None (requires intentional operator re-trigger). | Cycle transitions to `COLLECTION_FAILED`. Constituent IOUs remain untouched in ledger for subsequent clearing attempt. | Clearing Room displays: *"Operator Cancelled PayPal Checkout"*; allows fresh cycle creation. |
| **4. Capture Call Timeout** | Socket timeout ($\ge 15\text{s}$) on `POST /v2/checkout/orders/{id}/capture`. | `paypal_orders.status = 'APPROVED'` or uncommitted; cycle in `COLLECTION_PENDING`. | Retry capture with **exact same** `PayPal-Request-Id` (`"nexus_cap_" + cycle_id`). | Backend calls PayPal `GET /v2/checkout/orders/{id}` to inspect authoritative state. If status is `COMPLETED`, transitions to `CAPTURED`. | Shows "Verifying Capture with PayPal..."; resolves automatically. |
| **5. Capture Webhook Arrives Before API Return** | Webhook listener receives `PAYMENT.CAPTURE.COMPLETED` while browser redirect is still in-flight. | `paypal_orders.status = 'CAPTURED'`; cycle is `COLLECTION_CAPTURED`. | Webhook commits state immediately. API return path detects status already `CAPTURED`. | Both paths operate inside `BEGIN IMMEDIATE` transactions. Path A or B acquires lock, updates state; second path exits as idempotent no-op. | Seamless UI update via SSE; zero error messages shown. |
| **6. Duplicate Capture Webhook** | Webhook listener receives identical `PAYMENT.CAPTURE.COMPLETED` with already processed event ID. | `processed_webhooks` table contains `paypal_event_id`. | None. Acknowledge with HTTP 200 immediately. | Unique index violation caught; handler discards duplicate and returns `{ "received": true, "duplicate": true }`. | No duplicate state mutation; logged to audit stream. |
| **7. Server Crash After Capture Call, Before SQLite Commit** | Process restarts. PayPal shows `COMPLETED`, but SQLite has `paypal_orders.status = 'APPROVED'`. | On boot, reconciler scans for cycles in `COLLECTION_PENDING` with an approved order. | Startup reconciler fires single check per pending order. | Reconciler calls PayPal `GET /v2/checkout/orders/{id}`. PayPal confirms `COMPLETED`. SQLite updates to `CAPTURED`. | System recovers on boot; Clearing Room displays verified captured state. |
| **8. Payout Dispatch Timeout or HTTP 5xx** | Socket timeout ($\ge 15\text{s}$) or HTTP 500/503 on `POST /v1/payments/payouts`. | `settlement_cycles.status = 'COLLECTION_CAPTURED'`. No payout record committed locally. | Re-send with **exact same** `PayPal-Request-Id` and `sender_batch_id`. | If PayPal created the batch, it returns HTTP 400 `DUPLICATE_SENDER_BATCH_ID` with HATEOAS link `rel: "batch"`. Reconciler queries that link (`GET /v1/payments/payouts/{id}`) and recovers authoritative batch state. | Shows "Reconciling Payout Batch with PayPal..."; zero risk of duplicate payout. |
| **9. Duplicate Payout Dispatch Attempt** | User or agent double-clicks "Dispatch Payouts". | Financial Firewall checks active cycle status. | Rejected locally by Financial Firewall before network call. | Firewall denies call because cycle is already in `PAYOUT_DISPATCHED` or `RECONCILING`. | UI button disables immediately upon first click; error toast if forced. |
| **10. Payout Batch Accepted with Pending Items** | PayPal Payouts returns HTTP 201 `batch_status: "PENDING"` or `"PROCESSING"`. Items still processing. | `paypal_payouts.status = 'PENDING'` / `'PROCESSING'`; cycle is `RECONCILING`. Items in `PENDING`. | Polling reconciler checks `GET /v1/payments/payouts/{batch_id}` every 3,000ms. | Cycle **cannot** transition to `SETTLED` while items are pending or processing. Reconciler waits until all item webhooks or polling confirm final status. | Clearing Room displays: *"Reconciling Creditor Payouts (4 items processing)..."*. |
| **11. Payout Item Unclaimed (Unregistered Sandbox Email)** | PayPal reports `status: "UNCLAIMED"` (recipient email not yet registered). | `paypal_payout_items.status = 'UNCLAIMED'`; cycle in `RECONCILING` with hold flag. | Wait 30-day window or sender cancellation. Child reissue is STRICTLY PROHIBITED while UNCLAIMED (`trg_reissue_parent_terminal_check` aborts attempt). | Funds remain encumbered at PayPal. Reconciler preserves item in `UNCLAIMED`. Cycle does NOT settle until claimed or returned. Reissue allowed only post-terminal return. | Amber badge: *"Payout Unclaimed — Awaiting Recipient Sandbox Wallet (Reissue Prohibited)"*. |
| **12. Payout Item Held (Compliance Review)** | PayPal reports `status: "ONHOLD"` via webhook `PAYMENT.PAYOUTS-ITEM.HELD`. | `paypal_payout_items.status = 'ONHOLD'`; cycle remains in `RECONCILING`. | Background polling pauses for this item; alerts operator. Child reissue is STRICTLY PROHIBITED (`trg_reissue_parent_terminal_check` aborts attempt; guarantees duplicate disbursement if AML review clears). | Reconciler flags item for operator inspection. Payout is not treated as failed unless PayPal resolves to FAILED/BLOCKED. | High-visibility warning: *"Payout Held by PayPal for Compliance Review — Reissue Strictly Prohibited"*. |
| **13. Individual Payout Item Failure (Invalid Account)** | PayPal reports `status: "FAILED"` or `"BLOCKED"` via webhook. | `paypal_payout_items.status = 'FAILED'` / `'BLOCKED'`; cycle is `PARTIAL_FAILURE_HOLD`. | Do not retry automatically (invalid recipient cannot be solved by retrying). | Residual collected funds remain quarantined in ledger. Cycle locked in `PARTIAL_FAILURE_HOLD`. Operator must resolve recipient details. | Prominent red alert: *"Payout Item Failed for Data Agent — Cycle on Hold"*. |
| **14. Payout Item Returned, Refunded, or Reversed** | Unclaimed 30d window expires (`RETURNED`), recipient refunds payment (`REFUNDED`), or PayPal administrative chargeback (`REVERSED`). | `paypal_payout_items.status = 'RETURNED' / 'REFUNDED' / 'REVERSED'`; cycle updates to `POST_SETTLEMENT_RECONCILING`. | None. | Atomically records compensation entry in `compensating_ledger` restoring cash to `ASSET:PAYPAL_SETTLEMENT_CASH` and reinstating `LIABILITY:CREDITOR_PAYABLE`. Historical settled receipts remain immutable. | UI displays: *"Post-settlement reversal processed — liability reinstated for operator reissue"*. |
| **15. Webhook Processing Failure / SQLite Crash** | SQLite fails during webhook processing or machine crashes mid-transaction. | SQLite rolls back entire `BEGIN IMMEDIATE` transaction. | PayPal webhook retry mechanism automatically re-delivers event with backoff. | Because `processed_webhooks` rolls back atomically with domain tables, PayPal's next retry re-attempts full processing. No event is permanently lost. | Error logged to server monitoring; recovers automatically upon redelivery. |
| **16. Webhook Cryptographic Verification Failure** | Incoming webhook has invalid signature, tampered payload, or expired cert URL. | Webhook rejected. No database mutation occurs. | Respond with HTTP 400 Bad Request. | Handler logs security alert with IP, transmission ID, and header payload. Rejects spoofed events. | Security console logs: *"Untrusted Webhook Dropped — Verification Failed"*. |
| **17. Complete PayPal Sandbox Outage / Network Drop** | DNS failure or HTTP 503 / connection refused from `api-m.sandbox.paypal.com`. | Local ledger remains fully consistent; state transitions freeze safely. | Exponential backoff for background reconciler. | System transitions gracefully to `MOCK_SETTLEMENT` mode **if explicitly enabled by operator**, otherwise holds state pending recovery. | Clear banner: *"PayPal Sandbox Unavailable — Financial Operations Paused"*. |
| **18. Premature Reissue / Concurrent Reissue Race / Ambiguity** | (a) Premature reissue attempt while parent is in `PENDING`, `ONHOLD`, `UNCLAIMED`, `AMBIGUOUS_HOLD`, or `SUCCESS`; (b) Concurrent second child reissue attempt while child is active; (c) Network failure or 5xx during child reissue dispatch. | (a) HTTP 409 `REISSUE_PROHIBITED_PARENT_NOT_TERMINAL` or trigger `trg_reissue_entitlement_check` `ABORT`; (b) SQLite `UNIQUE constraint failed: uq_active_child_per_parent` or HTTP 409 `REISSUE_ENTITLEMENT_LOCKED`; (c) `paypal_payout_reissues.status = 'AMBIGUOUS_HOLD'`. | (a) Reissue strictly blocked until parent reaches `REISSUE_AUTHORIZED` via atomic return verification; (b) Exactly one active child allowed; (c) Exponential backoff polling by `sender_item_id`. | Engine queries PayPal by deterministic `sender_item_id`. No duplicate payout is dispatched. Reissue is authorized only upon verified terminal return of parent principal. | Yellow indicator: *"Reissue Verification Pending — No Duplicate Dispatched"*. |
| **19. Dual-Success Collision (Original Late Success vs Reissue)** | Original payout item receives late `ITEM.SUCCEEDED` after child reissue was already dispatched. | Detected via `paypal_payout_items.active_reissue_id` being non-null. | Automated processing halted immediately. | Engine blocks double liability extinction. Flags `CRITICAL_DUAL_DISBURSEMENT_COLLISION`, moves cycle to `OPERATOR_DISPUTE_HOLD`, and records excess funds as operator dispute receivable. | Red banner: *"Dual Payout Collision Detected — Manual Dispute Review Required"*. |
| **20. Partial Reversal Reference Collision** | Multiple partial reversals share same transaction ID or lack provider sub-refund ID. | Webhook contains transaction ID without unique refund ID. | Halted prior to ledger insertion. | System requires signed `operator_correction_ref` via `/api/settlement/operator-compensation` and asserts cumulative reversal $\le$ item principal. | Operator console alert: *"Provider Sub-Reference Missing — Operator Signature Required"*. |
| **21. Verified Provider Reporting Discrepancy** | Reconciler evaluates reporting snapshot from `GET /v1/reporting/balances`. Stale snapshots are labeled `STALE_REPORTING_DATA`. Snapshots refreshed after dispatch but awaiting transaction inclusion are labeled `PENDING_PROVIDER_REFLECTION`. If >3h elapses without reflection confirmation, status becomes `REFLECTION_TIMEOUT` (warns operator; does not halt clearing). Only snapshots with confirmed transaction completeness and unexplained $\Delta_{\text{Available}} \neq 0$ trigger `OPERATOR_DISPUTE_HOLD` (`DISCREPANCY_DETECTED`). | `settlement_cycles.status = 'OPERATOR_DISPUTE_HOLD'`; variance snapshot logged in `lifecycle_transitions` as `RECONCILIATION_SNAPSHOT`. | Periodic background audit; waits for transaction reflection completeness or operator manual audit. | Financial Firewall halts subsequent clearing cycles; recovers when fresh statement resolves variance to $0 or operator submits signed adjustment ticket via `/api/settlement/operator-compensation`. | Amber badge if stale, pending reflection, or timeout: *"Reporting Data Pending Provider Reflection"*. Red alert if verified discrepancy: *"Verified Balance Discrepancy — Clearing Paused"*. |
| **22. Crash During Shortfall Capital Cure** | Server crashes after physical funding succeeds on PayPal but before local ledger posting commits. | External funding confirmed (`cure_intents.status = 'FUNDING_CONFIRMED'`), but internal ledger unposted. `OPERATOR_DISPUTE_HOLD` preserved. | Reconciler checks `cure_intents` on reboot; replays journal entry idempotently. | Hold is NOT released until internal ledger and physical evidence reconcile. Prevents unrecorded equity injections and phantom cures. | Operator banner: *"Shortfall Cure Reconciling — Resuming Interrupted Journal Post"*. |
| **23. Reserve Floor / Liquidity Breach on Payout Dispatch** | Pre-dispatch evaluation detects `OPERATOR_CASH` - estimated fees $< \$10.00$ or multi-tier freshness gate detects $PP_{\text{Est\_Physical\_Available}} < \text{SETTLEMENT\_CASH} + \text{OPERATOR\_CASH}$ ($PP_{\text{Est\_Physical\_Available}} = PP_{\text{Reported}} - \sum \text{Dispatches} + \sum \text{Captures}$). | `settlement_cycles.status = 'OPERATOR_RESERVE_HOLD'`. Payout batch record NOT created. | Blocked locally before calling PayPal API. | Financial Firewall halts dispatch. Operator must inject capital via `POST /api/settlement/cure-custodial-shortfall` to restore operating buffer $\ge \$10.00$ and cover physical requirements. | High-visibility amber banner: *"Payout Dispatch Blocked — Operator Reserve Floor Breach ($10.00 Minimum Buffer)"*. |
| **24. Concurrent Payout Dispatch Race** | Two simultaneous payout dispatch requests submitted for different or same cycle. | Serial mutex `active_cycle_lock` detects `COUNT(*) > 0` in active dispatch state. | Rejected immediately before network call with HTTP 409 Conflict. | Second request rejected; zero duplicate API submissions or double-fee encumbrance. | Toast notification: *"Concurrent Dispatch Blocked — Cycle In Progress"*. |
| **25. Premature Recovery Recognition / Missing Evidence / Invalid Transition** | Attempt to advance recovery claim to Stage 5 under `US_GAAP_CONSERVATIVE` (where Stage 5 is skipped), or advance to Stage >= 4 without complete non-null documentary evidence (`stage4_evidence_type`, `stage4_evidence_hash`, `authorization_role`, `authorizer_id`, `stage4_evaluated_at`), or attempt invalid transition `from_stage != current_stage`, or mutate `recovery_claim_events` directly. | Request rejected with HTTP 422 Unprocessable Entity or SQLite trigger `ABORT`. In `recovery_claims`, `recognized_receivable_cents` remains 0; stage remains in 1–4. | None. Await physical cash collection (GAAP Stage 6) or certified legal evidence (IFRS Stage 5). Stage 6 permits partial collection with remaining residual balance closed via Stage 6 -> 7. | Schema CHECK constraints and triggers strictly prevent pre-collection asset creation, evidence bypass, invalid transitions, sequence gaps, or direct updates/deletions on audit events. | Audit log: *"Premature Recovery Recognition Blocked — Realization Standard & Trigger Enforced"*. |

## 2. Invariant Safety Guarantees

1. **No Phantom Disbursements:**
   Payouts use stable, deterministic `sender_batch_id` values derived from `cycle_id`. Even under network timeouts or server crashes, PayPal's server-side deduplication guarantees that a batch is executed at most once.
2. **Authoritative External Settlement Source:**
   Local ledger status is subordinate to authoritative PayPal API query results. In any divergence between local memory and PayPal's REST endpoints, PayPal's confirmed status (`COMPLETED`, `DENIED`, `SUCCESS`) is adopted.
3. **No Unfunded Payout Execution:**
   The Financial Firewall strictly asserts that `paypal_orders.status == 'CAPTURED'` with verified captured USD cents before allowing the dispatch of a payout batch.
